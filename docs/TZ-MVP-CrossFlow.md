# ТЕХНИЧЕСКОЕ ЗАДАНИЕ · MVP

| Поле | Значение |
|------|----------|
| Проект | B2B-платформа кросс-маркетинга и партнерских цепочек |
| Рабочее название | **Dante Florens · Дарующий расцвет** (внутреннее: CrossFlow) |
| Версия документа | **1.0** |
| Статус | Готово к оценке сроков/бюджета |
| Горизонт MVP | 8–10 недель до закрытой беты |
| Пилот | 1 город-миллионник, 5 ниш, 50 компаний |

---

## 0. Резюме для оценки

**Что строим:** веб-приложение (адаптив + Telegram Mini App / WebApp), где МСБ обменивается клиентским потоком через подарочные сертификаты и многосторонний клиринг баллов, без прямого рекламного бюджета.

**Чего не строим в MVP:** полноценный маркетплейс курсов, глубокие интеграции с кассами (iiko / Эвотор), лицензирование методик внешних спикеров, микросервисный зоопарк.

**Критерий успеха пилота:** ≥50 компаний в одном городе; ≥10 связок с погашенными купонами; измеримая воронка «выдано → активировано → погашено → сумма чеков».

---

## 1. Цели и границы

### 1.1. Бизнес-цели

1. Дать предпринимателю способ привлекать клиентов через партнёров без CPC.
2. Снять главный блокер классического бартера — несовпадение объёмов трафика — через **балльный клиринг**.
3. Зафиксировать доходимость до кассы и выручку с кросс-маркетинга в цифрах.

### 1.2. UVP

Автоподбор неконкурентных партнёров со смежной ЦА → генерация оффера/скриптов ИИ → уникальный смарт-купон → прозрачный трекинг до кассы.

### 1.3. Вне scope MVP (явно)

| Не делаем сейчас | Когда |
|------------------|-------|
| Нативные приложения iOS/Android | После product-market fit |
| Полная интеграция iiko / R-Keeper / Эвотор | Этап 2 |
| CPA-комиссия с чека в авторежиме (эквайринг split) | После стабильного трекинга |
| Витрина курсов с оплатой 20–30% | Этап 2 (медиа-контур) |
| Лицензирование методики конкретного спикера внутри продукта | Отдельный коммерческий договор, не блокер MVP |
| Микросервисная архитектура «с нуля» | Модульный монолит |

### 1.4. Допущения (зафиксировать до старта разработки)

1. **География:** локальный пилот в **одном** городе (не nationwide day-one).
2. **Ниши пилота:** бьюти, авто, общепит, фитнес, медицина/стоматология (или эквивалентный кластер по решению основателя).
3. **Стек реализации:** предпочтительно эволюция существующего контура `dante-florens` (Node) **или** greenfield Next.js + FastAPI/Nest — решение на kickoff; ТЗ функционально-нейтрально.
4. **ИИ:** внешние LLM API + RAG по внутренней базе кейсов; без собственного fine-tune модели в MVP.
5. **ПДн:** хранение и обработка по 152-ФЗ на инфраструктуре в РФ.

## 2. Роли и права

| Роль | Описание | Ключевые права |
|------|----------|----------------|
| **Owner / Маркетолог** | Владелец или сотрудник компании-участника | Профиль, офферы, сделки, аналитика, биллинг |
| **Кассир / Сотрудник** | Гасит купоны без полного кабинета | Только страница сканера/кода |
| **B2C-получатель** | Конечный клиент с подарком | Активация сертификата (телефон / Telegram), предъявление QR |
| **Эксперт / Трекер** | Амбассадор, приводит бизнесы | Реферальная ссылка, витрина профиля, базовая статистика привлечённых |
| **Super-Admin** | Операторы платформы | Модерация компаний, тарифы, промпты, антифрод, арбитраж |

Модель доступа: RBAC + привязка пользователя к `company_id`. Один пользователь может быть связан с несколькими компаниями (этап 2 — опционально; в MVP — 1 компания = 1 основной Owner).

## 3. Пользовательские сценарии (Must-have)

### US-01. Онбординг бизнеса
Как Owner, я регистрируюсь по телефону или Telegram, указываю ИНН (автозаполнение реквизитов), заполняю паспорт активов и попадаю в ленту партнёров.

**Приёмка:** регистрация < 3 минут; профиль сохраняется; без заполненного паспорта матчмейкер недоступен (мягкий блок с подсказкой).

### US-02. Подбор партнёра
Как Owner, я вижу ленту рекомендованных партнёров с индексом совместимости и причиной («смежная ЦА, нет прямой конкуренции»).

**Приёмка:** топ-N карточек; исключение той же ниши/прямых конкурентов по правилам; ручной поиск по нише/району.

### US-03. Создание связки
Как Owner, я нажимаю «Создать связку», ИИ генерирует текст сертификата, скрипт кассира и текст рассылки; я редактирую и публикую оффер.

**Приёмка:** ответ генерации ≤ 15 сек (p95); результат сохраняется как черновик/оффер; можно править вручную.

### US-04. Сделка 1↔1 и клиринг
Как Owner, я принимаю условия оффера партнёра (акцепт) либо участвую в пуле: за погашенный у партнёра купон получаю баллы (Lead-coins), трачу их на размещение своего оффера у других.

**Приёмка:** статусы сделки видны обеим сторонам; баллы начисляются только после **погашения**; двойного начисления нет.

### US-05. Выдача и активация купона (B2C)
Клиент сканирует QR / переходит по ссылке → лендинг с таймером → «Забрать» → ввод телефона или Telegram → получает уникальный код/QR.

**Приёмка:** один код = один купон; повторная активация с того же номера по той же связке — по правилу (блок или продление — конфиг Admin).

### US-06. Гашение на кассе
Кассир открывает короткую ссылку сканера, вводит/сканирует код, указывает сумму чека, гасит.

**Приёмка:** погашенный купон нельзя погасить повторно; сумма чека пишется в аналитику; Owner видит событие в дашборде ≤ 1 мин.

### US-07. Аналитика воронки
Как Owner, я вижу по каждой связке: выдано → активировано → погашено → сумма чеков → упрощённый ROI.

**Приёмка:** цифры сходятся с журналом событий; экспорт CSV (желательно в MVP).

### US-08. Подписка Pro
Как Owner, я оплачиваю Pro через ЮKassa/Тинькофф; лимиты Start снимаются; чек 54-ФЗ формируется.

**Приёмка:** рекуррент или ручное продление (допустимо v1 без auto-renew, если зафиксировано); даунгрейд при неоплате по правилам тарифа.

## 4. Функциональные модули

### Модуль 1. Онбординг и профиль бизнеса

- Auth: SMS/звонок и/или Telegram Login / Telegram ID.
- ИНН → DaData (или аналог): юр. название, адрес, ОГРН/КПП где применимо.
- **Паспорт активов:**
  - ниша, средний чек, ЦА (пол, возраст, интересы — словарь + свободный текст);
  - гео (город, район);
  - точки контакта: трафик/день, база CRM (объём), соцсети, упаковка, зона ожидания;
  - скрытые ресурсы: недозагрузка, товар/услуга-локомотив (себестоимость/ценность).
- Статусы компании: `draft` → `pending_moderation` → `active` / `blocked`.

### Модуль 2. AI-двигатель

**2.1. AI-Матчмейкер — два режима**

- **Смежные ниши (adjacent):** вход — паспорт; выход — неконкуренты со смежной ЦА + score + обоснование. Жёсткое исключение той же узкой ниши (классический кросс-маркетинг).
- **Коллеги по нише / коопетиция (coopetition):** тумблер в UI. Подбор только same-role / близкий craft. Скоринг: другой район, открытый слот перегрузки, окна простоя. Клон «всё то же + тот же район» — вниз списка.
- Хранение MVP: SQLite docs + правила; этап 2 — эмбеддинги / pgvector.

**2.2. «ИИ-Расцвет» — генератор связок**

- Триггер: «Создать связку с партнёром X» (+ template в режиме коопетиции).
- Выход: 3 оффера, скрипт персонала, текст рассылки; для коопетиции — пакт, якорь возврата, protected services.
- Стек: шаблоны + LLM API (system prompt в `docs/AI-CROSSFLOW-PROMPT.md`).

**2.3. Шаблоны коопетиции (пример: частные клиники, применимо к любой нише)**

| Шаблон | Боль | Решение | Биллинг |
|--------|------|---------|---------|
| **overflow** | Нет окна / отказной трафик | Заботливый сертификат коллеге со свободным креслом | RevShare 15–20% или ×1.5 Лид-коины |
| **specialty** | Нет оборудования / редкого врача | Направление-подарок + якорь возврата + запрет переманивать | Lead-coins |
| **geo** | Неудобный район на курс | Передача коллеге в другом районе | RevShare с курса |

### Модуль 3. Биржа коллабораций, коопетиция и сделки

- Конструктор оффера: подарок, условия, лимит выдач, срок, мин. чек.
- Типы сделок MVP:
  - **Direct** — взаимный обмен 1↔1;
  - **Pool** — Lead-coins за погашение;
  - **Coopetition** — коллеги по нише с протоколом доверия;
  - **Hot handoff** — слот перегрузки + именной талон.
- **Протокол доверия (обязателен при publish coopetition):**
  1. Защищённый профиль — список услуг отправителя, которые получатель не предлагает этому контакту (`pactBans`);
  2. Якорь возврата — отложенный бонус обратно к отправителю (на лендинге купона);
  3. Журнал акцепта пакта (`pactAcceptedAt`).
- **Слот перегрузки:** Owner открывает «свободно сегодня» (услуга + район). `POST /handoff` (услуга + район/срочность) → лучший open-слот → published bundle + опциональный claim.
- Акцепт оферты = запись условий + timestamp. Юридика пакта — зона юриста; в продукте — продуктовый флаг + журнал.

**Правила Lead-coins и RevShare (MVP):**

| Событие | Начисление |
|---------|------------|
| Погашение купона (adjacent / specialty) | +N Лид-коинов отправителю |
| Погашение hot / overflow с RevShare | % от чека → коины + поле `revshareAmount` |
| Hot без RevShare | ×1.5 к обычным коинам |
| Размещение оффера у партнёра | −K баллов |

Баллы **не** выводятся в рубли в MVP (RevShare учитывается в ledger как ценность).

### Модуль 4. Трекинг и гашение (B2C)

- Уникальный купон: `code` (6–8 символов) + QR + short URL.
- Лендинг сертификата: оффер, партнёры, таймер, CTA активации.
- Кассир-сканер: отдельный URL с токеном компании/точки; без полного ЛК.
- Журнал событий: `issued` | `activated` | `redeemed` | `expired` | `cancelled`.
- Webhooks наружу (amoCRM / Битрикс24) — **Should**, не блокер пилота; контракт API описать, реализация — по приоритету.

### Модуль 5. Каталог трекеров (урезанный MVP)

Открытый контур, без привязки методики к одному имени.

Must:

- Профиль сертифицированного трекера (модерация Admin).
- Реферальная ссылка → атрибуция компании → % от подписки Pro (начисление в кабинете; выплата — вне продукта или реестр к выплате).

Should / этап 1.5:

- Каталог сертифицированных трекеров и экспертов по кросс-маркетингу и монетизации скрытых ресурсов. Заявка на разбор — форма, без эквайринга курсов. Условия партнёрства одинаковые для любого практика, прошедшего модерацию.
- Витрина кейсов: ручная публикация Admin + авто-черновик из статистики при согласии компаний.

Won't в MVP: магазин курсов с комиссией 20–30%.

### Модуль 6. Биллинг

| Тариф | Лимиты (ориентир, прайс — конфиг) |
|-------|-----------------------------------|
| **Start** | 1 активный оффер, ≤30 выдач купонов/мес, базовый поиск |
| **Pro** | безлимит связок (fair use), ИИ-генератор, полная воронка |

- Платёжный шлюз: ЮKassa и/или Тинькофф Касса.
- Чеки 54-ФЗ через шлюз.
- Денежный split с чека через эквайринг — **не** в MVP. В коопетиции доля с чека пишется в журнал как Лид-коины (`revshareAmount`), не как выплата на счёт. Поле `attribution` и событие `redeemed` остаются для будущего биллинга.

## 5. Аналитика (дашборд)

Метрики на связку и агрегат по компании:

1. Выдано (scan/click стартового QR/ссылки).
2. Активировано (телефон/Telegram получен).
3. Погашено.
4. Сумма чеков (введённая кассиром).
5. Конверсии между шагами.
6. Lead-coins: баланс, начислено, списано.
7. Оценка отдачи: `(сумма подтверждённых чеков − оценка себестоимости подарков) / стоимость подписки за период`. Знаменатель никогда не ноль. На экране пометка «оценка», пока себестоимость подарка не внесена в паспорт.

Admin-дашборд: компании, аномалии антифрода, MRR, воронка пилота.

## 7. API (контур)

Стиль: REST JSON (+ опционально webhooks). Черновой список групп:

- `POST /auth/*` — OTP, Telegram
- `CRUD /companies`, `PUT /companies/:id/passport`
- `GET /matches` — лента матчмейкера
- `POST /ai/bundle` — генерация связки
- `CRUD /offers`, `POST /deals/:id/accept`
- `POST /coupons/issue`, `POST /coupons/activate`, `POST /cashier/redeem`
- `GET /analytics/funnel`
- `POST /billing/checkout`, webhooks платежей
- `Admin/*` — модерация, тарифы, промпты

Идемпотентность на `redeem` и платежных webhooks — обязательна.

## 11. Roadmap продукта после MVP (не оценивать в смете MVP)

- Месяц 2 пилота: консьерж-сведение 50–100 компаний, офлайн-практикум, 10 кейсов.
- Месяц 3: партнёрка трекеров в другие города.
- Этап 2: кассы/CRM webhooks deep, CPA с чека, маркетплейс разборов, усиленный антифрод (гео при redeem).

## 12. Риски и ловушки

1. **Перегруз MVP ИИ и «клубом экспертов»** — пилот держится на выдаче/гашении и 2–3 живых связках, не на медиа.
2. **Фрод баллов** — без жёсткой привязки начисления только к `redeemed` экономика пула развалится.
3. **Юридика подарков/персональных данных** — нужна оферта и согласие; продукт не заменяет юриста.
4. **Зависимость от звезды-амбассадора** — в ТЗ MVP амбассадор = рефка + контент снаружи, не лицензия методики в коде.
